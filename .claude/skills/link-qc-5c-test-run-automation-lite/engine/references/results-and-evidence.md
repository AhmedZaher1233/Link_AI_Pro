# Results, evidence and the logs (rules)

Loaded at **Reviewing Requirements & Test Cases**: the phase number, the three roots, the whitelist, the evidence contract. `run-report.md` (report shapes, renderer, run-file schema) is loaded only at **Preparing Final Report**. Detail: `references/maintainers/results-and-evidence.md`.

<result_organization>
**All run artifacts per User Story, immutable phase history, under the structure's `reports/` folder mirroring the TC folder's `SPEC-*` parent.** `run-report.md` owns the folder contract (§3) and the run-file schema.

- `{results_root}` = `{automation_root}/reports/{spec_level}{user_story_name}/` — the TC folder's exact leaf, resolved once, immutable for the run.
- **Every invocation is a NEW phase.** `N` = 1 + the highest phase in `{results_root}/.runs/phase-*.json`, legacy top-level `phase-*.json|html` and every `{legacy_results_root}`. Resolve N once at profile time, create `.runs/phase-{N}.json` (`status: planning`), write only to `{results_root}`. **NEVER overwrite, edit or delete a previous phase's artifacts.** An invocation that stops before execution still finalizes a short phase (run file with its final status, a `## Phase N` section whose Outcome says why, a run-history row of `—`); the next takes N+1.
- Inside `{results_root}`: `TEST-RUN-REPORT-{feature}.md` (header + `## Run history` + one `## Phase N` per run, appended) · `BUG-REPORT-{feature}.md` · `TEST-RUN-REPORT-{feature}.html` · `automation-inventory.md` · `coverage/` (three CSVs, replaced) · `.runs/phase-{N}.json` (immutable once final; skill 9's retest of the latest phase excepted) · `artifacts/` (`stages/`, `progress/`, `drafts/`, `checks/`, `test-output/`). No `SPEC-*` parent → flat; an old `US-{id}/` leaf is read-only history.
- **Top-level whitelist:** exactly those files plus the reviewer's optional `REVIEW-COMMENTS-{feature}.md` (never created by the skill; only each handled entry's Status and Response are set). Nothing else. Gate records: `.runs/phase-{N}.checkpoint-{A|B}.json`; run scratch, drafts and snapshots under `artifacts/`; a scratch probe never here (`<scratch_investigation>`).
- The manual CLI run (5b) shares this folder, phase counter and `BUG-{n}` sequence; its phases are ordinary earlier phases.
- **Legacy locations are read-only history:** `reports/[SPEC-*/]US-{id}/`, top-level `phase-N.json|html`, `merged-results.json`, `run-plan.json`, `open-questions.json`, `data-readiness.json`, `stages/`, `coverage/coverage-dashboard.html`, `coverage-previous.json`, legacy `automation-logs/…/US-{id}/` and `screenshots/` leaves stay exactly where they are; never moved, renamed, deleted or rewritten. The first run under the new layout says so once in chat, names them on the report header's `Earlier phases` line and in `{run_file}.previous_phase`, and reads a legacy `coverage-previous.json` only as the coverage-delta fallback (stated).
- At finalization: complete the run file, append the `## Phase N` section, update the bug file, render (`<second_run>` step 4). The phase number appears in the run file (`"phase": N`), the `## Phase N — date` heading, a run-history row, the page, the ADO comment and the final chat summary.

**Screenshots — every TC, variant and attempt the run's screenshot choice owes (`all` by default); one folder per User Story; IMMUTABLE.**
Path: `{screenshots_root}/phase-{N}/{TC-ID}/{variant_slug}/attempt-{a}.png` (ASSERTION-POINT image, full page, pass or fail) and `attempt-{a}-failed.png` (the failing step), plus `phase-{N}/variants.json` (slug → title path, project, spec file). A second-locale variant is its own TC. API / DB records sit beside the image path: `attempt-{a}.record.json` / `attempt-{a}-failed.record.json` (schema `skill5-record/1`, redacted, sealed, never overwritten); a backend TC has records and no image, a hybrid TC both; a backend slug reads `backend--…--r0`.
`variant_slug` = `{project}--{data-variation-slug}--r{repeat}` (`testInfo.project.name`; kebab-case of the variation label in the title, `none` without one; `testInfo.repeatEachIndex`). `{a}` counts every execution of that variant in this phase from 1, in command-start order (first run, isolation check, smoke retry, re-queue, re-run, each burn-in repeat, Playwright retries). A burn-in repeat's image lands under its own `r{repeat}`; the merge credits it to the required variant as an attempt. Which image belongs to which attempt is decided by the attempt's test span (TC, project, repeat, retry, worker), never by the folder alone (`references/schemas/paths-and-evidence.md` §1, §4-§5).

**Evidence contract — the screenshot is taken at the ASSERTION POINT, never at test end** (a post-teardown image contradicts the PASS it is attached to):
- The helper is the skill's template `assets/evidence.template.ts`, installed as `helpers/evidence.ts` by `config-inventory.mjs reconcile --apply` (`captureEvidence(page, testInfo)`, or the project's equivalent). It captures at the assertion point, writes under EACH `[TC-ID]` of the title, never to an existing path (it increments `{a}`), records the slug in `variants.json`, and writes exactly ONE `evidence` heartbeat (`{ at, worker, tc, event: 'evidence', path }` via `helpers/steps.ts` `heartbeat()`) per attempt — the failure image writes none. The validator rule `evidence-helper-contract` fails a helper that emits two `evidence` events per attempt. The console guard's `report()` — the first statement of `afterEach` — writes `teardown`; Checkpoint B proves image-before-teardown from them (item 16b); without the heartbeat line 16b stays `unresolved`.
- The spec calls it **inside the test body at the assertion point** — immediately before the (last) `expect(...)` of the Assert step, while the verified state is on screen. One call per test; several screens → the last one. Order: **Arrange → Act → `captureEvidence` → Assert → teardown in `afterEach`/`afterAll`**. If the TC's own steps end with a delete, the screen that proves the removal IS the evidence.
- The `afterEach` hook does failure handling only: it copies Playwright's failure attachment to `attempt-{a}-failed.png` and, when the test failed before `captureEvidence`, writes the current screen as `attempt-{a}.png`. It never overwrites an existing image.
- The run's screenshot choice (`{run_file}.delivery.screenshots`, `intake.md` item 4) reaches every command as `PW_SCREENSHOTS` (absent → `all`) and the helper — never the spec — honours it: `all` → everything above; `failed` → `captureEvidence` writes nothing (no image, no `evidence` heartbeat), the failure hook still writes both images of a failing attempt; `none` → no image at all. Records are written whatever the choice. The spec code is identical under every choice. An existing helper that ignores `PW_SCREENSHOTS` gains that one guard when the run chose `failed` / `none`; until then it writes every image (more than owed, never less).
- Specs only call the helper — no `page.screenshot(...)` in a spec body.
- **Evidence sanity check (first run and re-run):** every PASS that has an image must show the state named in the TC's Expected Result, not a cleaned-up screen; otherwise `evidence_failure` (test-code defect — the call sits after teardown or navigation), self-healed by moving the call; never an `app_bug`, never shipped uncorrected. Under `failed` / `none` a PASS has no image — nothing to check; item 19 records exactly that.
- **Evidence is immutable history:** nothing under `{screenshots_root}` is ever overwritten or deleted; each phase writes only into its own `phase-{N}/`; the page links images by relative path. One exception — Checkpoint B check 18: when every missing image exists under another root with the same relative layout (the config sat elsewhere), `run-data.mjs finalize` moves the files under `{screenshots_root}/phase-{N}/`, records `evidence_relocated: {from, to, files}` in the run file, lists it under `### Deviations`, and the check PASSES — no re-execution, no new phase.
- Every attempt's exact image path is stored in `{run_file}.merged` (`variants[].attempts[].evidence_screenshot` / `failure_screenshot`), in `{run_file}.results[]` (`evidence_screenshot` = the status-of-record attempt — the latest by command start time) and as a relative link in the Evidence cell of the Results table. A TC not re-run keeps its first-run image; the parallel attempt of an isolation-checked TC stays linked in its history. Records follow the same rule (`evidence_record` / `failure_record`; rendered "View record", never as an image).
- A NOT_RUN or SKIPPED TC has no image; the report says so. Under `failed` a passing TC has none, under `none` no TC has one — the `### Run` bullet `Delivery` states the choice.
- **Report format:** under `delivery.report: md` no `TEST-RUN-REPORT-{feature}.html` is written (the markdown is the deliverable; the renderer's gate still checks it); an earlier phase's page stays untouched and no longer shows the latest phase (`stalePage`).

**Immutable vs replaced:** finalized run files, earlier Markdown phase sections, screenshots and logs are immutable (skill 9's retest of the LATEST phase excepted — it adds images, never replaces one); HTML is rendered again from Markdown; only coverage CSVs and artifacts scratch are replaced; legacy files stay read-only.
</result_organization>

<automation_logs>
**One log pair per run under `{automation_root}/automation-logs/{spec_level}{user_story_name}/` (the same leaf as `reports/` and `screenshots/`); history never overwritten.** Create them at the very start of the run and tell the user both paths at once (`Get-Content -Wait <path>` on Windows). One NEW pair per run; never append to or overwrite a previous run's log; a legacy flat `automation-logs/US-{id}/` folder is left as is.
- `run-progress-{YYYY-MM-DD-HHmm}.log` — machine lines written by `run-stage.mjs` (command start / stop / end, test starts and ends, waits, status lines); its first lines record the resolved `results_root`, `logs_root`, `screenshots_root` and the run start time. **Never read by the model**; open a command's `artifacts/diagnostics/…/playwright-output.log` only to diagnose a failure.
- `run-summary-{stamp}.log` — a fixed-format human summary of ≈ 40 lines written by the script beside it: one line per activity (`HH:MM:SS · activity · {name} · start` / `… · end · M:SS`), one per stage start (`{stage} · start · N TCs`) and end (`{stage} · end · pass P fail F skip S · wall M:SS · test time M:SS`), one per TC result (`TC-ID · PASS|FAIL|SKIP · 12 s · reason`), heal rows and gate verdicts (`gate · A · PASS · {snapshot}`). No heartbeats, no unit lines.
- Activity transitions, heal rows and gate verdicts are written with `node .claude/skills/link-qc-5-test-run-automation/scripts/run-stage.mjs activity --log {progress_log} --text "{activity name}"` at every transition — the orchestrator calls it instead of appending by hand.
- The return links the summary log FIRST, then the progress log.
</automation_logs>
