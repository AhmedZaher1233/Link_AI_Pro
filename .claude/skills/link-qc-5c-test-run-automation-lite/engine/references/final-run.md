# The re-run, the merge and the reports — PHASE 4 (rules)

Loaded at **Re-running Fixed & Impacted Tests** — or at a smoke-gate stop, where step 1 does not apply; `<second_run>` steps 2-4 are **Preparing Final Report**. Detail: `references/maintainers/final-run.md`.

## PHASE 4 — TARGETED RE-RUN (FINAL REPORT)

<second_run>
1. **Targeted re-run** — only the TCs the first run's result can no longer stand for. One phase, one `## Phase {N}` section, one report; the re-run's attempts merge into the first run's (step 2); every TC not re-run keeps its first-run attempt.
   1. **Select** on the healed code:
      ```text
      node .claude/skills/link-qc-5-test-run-automation/scripts/impact.mjs select --root {automation_root} --spec {spec files} --progress {results_root}/artifacts/progress --run-file {run_file}
      ```
      It returns `impact_level: file | method | branch` per stale TC and overall. A change inside a conditional branch that only one locale / role / variant takes marks stale only the TCs whose variant takes it (read from the test title); TCs it could exclude are listed in `fresh_by_branch[]`; when it cannot decide it falls back to file level and says so. **Re-run set** = `stale[]` (`unknown[]` tests are always stale; `expanded[]` adds every TC sharing a test with a selected one) ∪ `no_verdict[]` (NOT_RUN after a stop, interrupted, `rate_limited`) ∪ every `environment_failure` TC once `<environment_gate>` passes again ∪ the setup group of every re-run `serial:{gap}` TC (run `--run rerun --stage setup --groups setup:{gap}` first) ∪ the predecessors of every re-run chain follower. **`app_bug` failures are not re-run unless stale.** You may ADD a TC with a written reason (`rerun.reason: added`), never remove one the selection named. `outside_scope[]` → `### Deviations`, not run; `fresh_by_member_only[]` is not re-run (Checkpoint B reviews it); `never_run[]` keeps its NOT_RUN reason unless that reason is gone.
   2. **Refresh Checkpoint A's applicable checks on the changed files** (`compliance-checkpoints.md` §4a) before anything runs.
   3. **Re-run** each stage that has TCs in the set, in staged order (setup → smoke → gate → positive → negative), ONE delegated `run-stage.mjs --run rerun` call per stage (`<live_progress>`; no `--cwd`, the script passes the config) and one stage message labelled "re-run": `--run rerun --stage {S} --stage-tcs {…} --tcs {the set's TCs of S} --burn-in auto` with the first run's `--units` file (the call re-plans itself when the heal changed the code). **Burn-in:** a healed TC runs `--repeat-each=3` (own command per group, workers 1, ceiling × 3; **any failing repeat = FAIL**) ONLY when its Heal Log entry has `cause_class` `timing` / `flaky` / `race`; a `deterministic` heal (wrong locator, text or branch) runs once. `--burn-in auto` reads `{run_file}.heal_log[].cause_class`; an explicit `--burn-in TC-…` list is still accepted. The stage message lists, per TC, why it runs: `healed` · `impacted by {file}#{Class.method}` · `failed` · `impacted (file level)` (passed, stale only at file level). The isolation check runs inside every re-run call.
   4. **Empty set** → no call. State "Re-run not needed — no code changed after the first run and every TC has a verdict" in chat, in the `### Run` bullet `- **Re-run:** not needed — …` and in `{run_file}.impact`.
   5. **Automation failures still open** → heal iteration 2 → select again (only what became stale since re-run 1, plus new `no_verdict[]`) → re-run 2. **Maximum 2 heal iterations** per phase; what still fails is reported as-is.
   6. **A smoke-gate STOP in the re-run** (`<staged_execution>` step 2) keeps every fresh first-run result; only the stale TCs the stop prevented become `NOT_RUN` `not started: smoke gate failed (re-run)`.
2. **Merge every attempt of the phase** — `run-data.mjs merge` inside `finalize`, never by hand. Merge key (TC, required-variant slug); attempts ordered by command start time, the latest is the variant's status (a burn-in fails on any failing repeat); a required variant missing beside a PASS → `INCOMPLETE`; `rate_limited` stays INCOMPLETE; a `[HUMAN]`-step TC whose automated part passed is `PARTIAL — human step pending`; totals count TCs (`run-report.md` §7). Resolve every payload warning (`evidence-ambiguous`, `req-id-conflict`, `paths-normalized`, `unplanned-tc`), never paper over it.
3. **Your judgements — one validated file, never a hand edit of the run file.** Write `{results_root}/artifacts/judgements-phase-{N}.json` and pass it to `finalize --judgements` (or `run-data.mjs judge --run-file {draft run file} --judgements … --write`): each FAIL's `classification` (`<first_run>` catalogue), `root_cause`, `severity`, `assumption`; every `parallel_checks[]` `cause` / `resolution`; every watchdog / timeout event's classification; the complete `heal_log[]` (the nine columns of `automation-rules.md` §5 plus `cause_class`), `deviations[]`, `skips[]`, `unverified_assumptions[]`, `bugs[]` (`req_id` from the result row). Validated as a whole — an unknown TC, a value outside its vocabulary, an unclassified FAIL, a duplicate or contradiction → rejected, nothing written. Shape: `schemas/script-payloads.md` *Inputs*.
4. **The phase section, the bug file and the page — DRAFTS, published only after Checkpoint B** (`<publication>`):
   - the draft `TEST-RUN-REPORT-{feature}.md` is WRITTEN BY THE SCRIPT (`run-data.mjs report --write` inside `finalize`): header lines, ONE run-history row, the `## Phase {N}` section in the frozen order (Run — your extra bullets kept —, Stages + smoke gate, Run plan, Coverage, Results, then Unverified assumptions, Bugs, Heal log, Skips, Open questions, Test-data readiness, records, Deviations). Earlier phase sections are never touched; never paste fragments or rebuild a table by hand.
   - the draft `BUG-REPORT-{feature}.md`: after `run-data.mjs draft-init` (tolerates an existing draft folder: seeds only the missing files, lists the kept ones in `kept[]`) or a first `finalize`, write one `### BUG-n` entry in `<bug_report_format>` per NEW `app_bug` of this phase (`Found in phase: N`, `Status: open`, the failure image as a relative link — under `delivery.screenshots: none` the `Screenshot` field reads `none captured (screenshots: none this run)`); for every existing bug whose TC ran, a History line and its Status (`resolved (phase N)` only after a passing retest; ids continue across this skill and 5b). `finalize` refuses while a bug of `bugs[]` has no entry, keeps narratives as written and recomputes only the `**Latest phase:**` / `**Bugs:**` header lines; no bug yet → `## Bugs` / `none`. Never entered: unverified-assumption failures, `rate_limited` TCs, parallel interference.
   - **Reviewer comments** (`REVIEW-COMMENTS-{feature}.md` beside the report, or pasted in chat): read every open entry and every `- **Reviewer comment:**` bullet; handle each per `run-report.md` §9b (a run request = a new phase, "not a bug" is weighed against the requirement, a TC change is `answered` with the route to skill 3 `--revision`), then set only its Status + one-line Response. A comment never changes a bug's Status. "read my comments" alone runs this bullet and the render.
   - The HTML is never hand-written; act on the renderer's payload (`run-report.md` §2), never on the HTML. Under `delivery.report: md` no page is written; the renderer's payload is still the check.
</second_run>

<publication>
**Drafts → freeze → review → gate → publish — ONE command, `run-data.mjs finalize`, called twice.** The report set exists as drafts until Checkpoint B passed on exactly those bytes; nothing a reader sees claims a B verdict the gate did not give. A per-phase lock (`artifacts/checks/finalize-phase-{N}.lock`) keeps two finalizers apart. Activity 8 is a DELEGATED step: a fresh subagent receives the run-file path and ONE `finalize` command and returns a ≤ 6-line verdict; the main thread keeps judgements, the review and the return.
1. **Draft, number, write, freeze** (exit 4 `AWAITING_REVIEW` is the expected outcome):
   ```text
   node .claude/skills/link-qc-5-test-run-automation/scripts/run-data.mjs finalize --results-root {results_root} --phase {N} --feature {feature} --root . --files {final in-scope files} --tc {source_tc_doc} --data {TEST-DATA md} --req {REQ files} --inventory {reports_folder}/automation-inventory.md --require-steps --judgements {results_root}/artifacts/judgements-phase-{N}.json [--member-reviews {json}] [--lint]
   ```
   In order, stopping at the first failure: `draft-init` (missing files only) → `merge --write` → `judge` → the results-freshness check (`check.mjs freshnessCheck` ALWAYS writes `{run_file}.impact.final_check` — `{ outcome: FRESH | STALE, stale: [], fresh: N, checked_at }` on all-clear; nothing is ever copied into the run file by hand) → the pre-gate acceptance → `report --write` → the bug-file header → the draft page (renderer gate must PASS) → Checkpoint B (`check.mjs checkpoint --checkpoint B`: snapshot = the freeze, mechanical, runtime) → `AWAITING_REVIEW` with `semantic-B.template.json`.
2. **Review → gate → publish:**
   ```text
   node .claude/skills/link-qc-5-test-run-automation/scripts/run-data.mjs finalize {the same arguments} --review {results_root}/artifacts/checks/{snapshotId}/semantic-B.json
   ```
   On the FROZEN drafts only — nothing regenerated; any change since the freeze → BLOCKED, re-freeze with step 1. Validated batch → gate B → only on PASS `publish`: the drafts covered by THAT gate promoted byte for byte, the page rendered from them + the gate record and reproduced byte for byte, rollback on any mismatch → the final acceptance (`<run_acceptance>`). Exit 0 `PUBLISHED`; anything else publishes nothing. A hand-edited published page is never overwritten (`publish --force` only after telling the user what will be lost). **Markdown only** (`delivery.report: md`): both calls still run the renderer's gate on the drafts, no draft page is written, `publish` writes no page (`page: null`, `reportFormat: md`); say once that an earlier phase's page (`stalePage`) does not show this phase.
3. **Close-out** — the Azure DevOps close-out under `linked` (after B PASS), the learning write-back, then release the lease after teardown, clean-up and the quiet period: `node .claude/skills/link-qc-5-test-run-automation/scripts/capacity.mjs lease release --env-id {env_id} --run-file {run_file} [--quiet-ms {ms}]`.
4. **A phase that ends BLOCKED:** a new phase starts from `node .claude/skills/link-qc-5-test-run-automation/scripts/run-data.mjs handoff --run-file {run_file}` in a FRESH session — the orchestrator writes that line in the return and STOPS; phase 2 never runs in the same context.
</publication>

<bug_report_format>
Every `app_bug` entry in `{bug_report_md}` (`BUG-REPORT-{feature}.md`, one `### BUG-n` entry per defect; fields and status rules `run-report.md` §5):
- **Title — ONE plain sentence naming the user-visible symptom**, pattern `The system <doesn't do X> when <condition>` or `The system <does the wrong X> when <condition>`. **Never** an assertion string, locator, TC-ID or requirement code — `expect(...) failed` is evidence, not a title.
- **Steps to Reproduce** — numbered, starting at login, the nine canonical verbs of the test cases, followable without reading the automation.
- **Expected / Actual** — one simple sentence each; no stack traces, locators or framework vocabulary.
- **Supporting fields (all of them):** TC-ID · Requirement · Severity · Environment · Browser · Language mode · Build · Root cause · embedded failure screenshot · **Evidence** (where the raw assertion text, error message and log excerpt belong). No screenshot → say so plainly (`playwright.config.ts` must set `screenshot: 'only-on-failure'`); under `screenshots: none` the field reads `none captured (screenshots: none this run)`.
</bug_report_format>
