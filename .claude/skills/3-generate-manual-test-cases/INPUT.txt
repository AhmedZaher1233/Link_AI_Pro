SKILL: 3-generate-manual-test-cases
WHAT IT DOES: Designs complete manual test cases (all required locales) from the requirement,
validates them against the LIVE application via Playwright MCP, and delivers a markdown TC
document plus an HTML review page for HUMAN approval.

============================================================
INPUT — WHAT YOU MUST PROVIDE
============================================================

ALWAYS REQUIRED:
  1. Feature name / User Story ID          — what to design TCs for. Several stories at once is
                                             fine: they are SPLIT, one folder + document +
                                             review page per story, plus a cross-story summary.

PICK YOUR STARTING POINT (tell the skill which case applies):
  Case 1 — Manual TCs already exist:
      → give the TC source: file path, Azure DevOps test cases, Word document, or paste
        the TCs as text. The skill updates/normalizes them instead of starting over.
  Case 2 — No TCs and no spec file:
      → give the Azure DevOps story ID (or Word doc path). The skill retrieves the story,
        writes REQ-{id}.md into the requirements folder US-{id}-{name}/ (under
        SPEC-{spec-name}/ when the source was a spec file), and designs from it.
  Default — Spec/requirement file exists, no TCs:
      → give the spec path, or let the skill find it
        (Testing/Requirements/**/REQ-*.md, docs/specs/).
  No docx MCP attached? Export the .docx to markdown/text or paste its content — the skill
  asks for that instead of failing.

OPTIONAL FLAGS:
  --lang ar|en Language of the HTML review page (TEST-CASES / TEST-DATA markdown stay English).
  --revision   Apply the reviewer's corrections to the TCs they name (patch, never regenerate).
  --audit      Health-check only: reports the resolved profile, the entry case, existing
               deliverables, the planned TC count and coverage, and what WOULD be overwritten.
               Writes NOTHING — not even the learning file.

ASKED DURING THE RUN (before any live validation):
  2. Application base URL                  — reused from the learning file when recorded there;
                                             otherwise asked
  3. Username + password PER ROLE          — exact accounts used in the TC steps
                                             (ALWAYS asked fresh; usernames appear in the steps,
                                             passwords are NEVER written to any file)
  4. Is the story implemented?             — implemented / partially / not implemented /
                                             not sure (skill verifies live either way)
  5. Review page language                  — taken from --lang or a saved project preference
                                             when present (a saved Arabic preference applies
                                             even to an English REQ); asked ONLY when the
                                             requirement is written in Arabic and nothing is
                                             saved; the answer is saved to the learning file

  No Playwright MCP server attached? The skill detects that BEFORE asking for credentials,
  skips the ask, still designs and delivers the full document, and marks every TC
  "draft — not app-validated" with the reason.

OPTIONAL:
  - Learning file path                     — default from qa-manifest.json
                                             (Testing/project-learning.md, created by skill 1)

IF ANYTHING IS MISSING: the skill searches the learning file first, then asks you in ONE message
and WAITS. It never assumes. Your answers (never credentials) are saved to the file's
"Manual TC Model" section so they are not asked again.

============================================================
OUTPUT — WHAT YOU GET
============================================================
  Stories from a spec FILE (roots come from Testing/qa-manifest.json):
  Testing/Manual_Test/TestCases/SPEC-{spec-name}/   <- {spec-name} = spec file stem, kebab-case;
                                                       ALSO used when the REQ-*.md you give sits
                                                       under Testing/Requirements/SPEC-{spec-name}/
    US-{id}-{name}/                                 <- one per story (same name as skill 2's folder)
      TEST-CASES-{feature}.md   <- source of truth (Status: PENDING HUMAN REVIEW) — always English
      TEST-DATA-{feature}.md    <- plain-English test data per story: what data the TCs need,
                                   whether it exists (READY / MISSING / IMPOSSIBLE / UNKNOWN),
                                   problems, and how to create what is missing (e2e scenario /
                                   api / db / set directly / manual). Skill 6 starts from it.
      TC-REVIEW-{feature}.html  <- visual review page (coverage gauge, badges, what stays manual,
                                   test data) in the chosen language (Arabic pages are RTL)
    TC-GENERATION-SUMMARY.md    (only when several stories were run)

  Stories given as ADO IDs / Word / pasted text (no spec file, REQ directly under Requirements/):
  Testing/Manual_Test/TestCases/US-{id}-{name}/
    TEST-CASES-{feature}.md
    TEST-DATA-{feature}.md
    TC-REVIEW-{feature}.html
  Testing/Manual_Test/TestCases/TC-GENERATION-SUMMARY.md   (only when several stories were run)

  Testing/Requirements/[SPEC-{spec-name}/]US-{id}-{name}/REQ-{id}-{feature}.md (Case 2 only)
  Testing/project-learning.md <- updated: flows, UI behaviour, test data, locale notes, Q&A

  An existing document with Status: APPROVED is never overwritten — the skill stops and offers
  --revision, the Case 1 update route, or an explicit overwrite (which then needs skill 5
  --republish, because the published revision changed).

YOUR NEXT STEP: review, adjust Smoke / Automation Candidate markings, optionally fill the
"Data effect" (read-only / creates / modifies / deletes) and "Shared data" fields on TCs
that change or share data (skill 6 uses them to decide parallel vs one-after-another
execution; blank = it infers), check the Problems table in TEST-DATA-{feature}.md (fix or
accept each data gap — skill 6 will validate the MISSING / UNKNOWN items before running),
then set Status: APPROVED in the markdown — that unlocks skill 5 (publish to Azure DevOps)
and then skill 6 (automation).
