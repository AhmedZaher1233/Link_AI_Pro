SKILL: link-qc-3b-validate-manual-test-cases
WHAT IT DOES: OPTIONAL step after link-qc-3-generate-manual-test-cases. Walks an existing test-case
document through the RUNNING application with Playwright MCP — targeted discovery, not a replay —
sets each TC's validation state with evidence, corrects labels and missing steps, records
potential bugs, updates the test-data statuses, and patches the same files in place (markdown,
test-data file, re-rendered HTML page). Before or after human approval. It is NOT a gate:
skills 4 and 5 accept a document that never went through it.

============================================================
INPUT — WHAT YOU MUST PROVIDE
============================================================

ALWAYS REQUIRED:
  1. The TC document                       — a path to TEST-CASES-{feature}.md, OR a feature name /
                                             User Story ID (the skill finds the document under
                                             Testing/Manual_Test/TestCases/**/US-{id}-*/), OR a
                                             SPEC-{name}/ folder (every story inside is validated;
                                             one combined ask, per-story write-back).
                                             Status may be PENDING HUMAN REVIEW or APPROVED.

OPTIONAL FLAGS:
  --scope full|shared|<TC-ID,…>  Decide the scope yourself; the skill does not ask.
                                 full   = every common flow once + every TC's unique tail
                                 shared = walk the shared step prefixes once, propagate the
                                          corrected wording to every TC; tails not walked
                                          (best state "inferred", never "validated")
                                 <ids>  = those TCs fully, every other TC untouched
  --full                         Same as --scope full; on a re-run also re-walks TCs whose
                                 evidence is still fresh.
  --authorize-revision           On an APPROVED document: you already authorize the changes,
                                 so the skill patches without asking (Status becomes PENDING
                                 HUMAN REVIEW only if something actually changed).
  --lang ar|en                   Language of the re-rendered review page (default: English —
                                 never the document's "Review page language" line, a saved
                                 answer or an existing Arabic sidecar; only this run's flag or
                                 an explicit sentence switches it; the line is rewritten to
                                 what this run rendered).
  --audit                        Probe Playwright MCP and analyse the document only: reports
                                 the document state, the common flows, the recommended scope
                                 and what it would leave unvalidated. Writes NOTHING, asks
                                 for no credentials.

ASKED DURING THE RUN — ONE message, after the Playwright MCP probe:
  2. Application base URL                  — the TEST-DATA "[E1]" row; reused from the learning
                                             file when recorded there, otherwise asked and written
                                             into that row (each [E2], [E3]… row is its own
                                             service — never "the URL")
  3. Password PER ACCOUNT the TCs reference — the TCs say "Login as Administrator [A1]"; the
                                             username comes from TEST-DATA §1 (asked when that
                                             row says "unknown" and filled there). Passwords are
                                             asked fresh every run and NEVER written to any file;
                                             no username is ever written into a step
  4. Is the story implemented?             — only when the document's header says
                                             "not yet checked live"; the skill verifies live
                                             either way
  5. Environment notes                     — e.g. VPN, test tenant, build shown in the footer
  6. Scope                                 — only when no --scope / --full was given: ONE
                                             question with a recommendation (from case count,
                                             risk, role differences, unique behaviour — 15 cases
                                             is a heuristic) that says exactly which TCs the
                                             recommended scope leaves unvalidated
  7. Revision authorization                — only for an APPROVED document when changes are
                                             expected and --authorize-revision was not given;
                                             asked once with the concrete list of changes
  8. Re-validate TCs already validated by  — only when in-scope TCs carry evidence written by
     skill 3c (the playwright-cli validator)?  3c; shows which evidence is still current and
                                             which is stale, recommends skipping the current
                                             ones and re-validating the stale ones; a skipped
                                             stale TC stays draft (never counted as validated).
                                             Not asked with --full or an explicit "compare" /
                                             "validate again" instruction.

  No Playwright MCP server attached? The skill stops BEFORE asking for anything (BLOCKED, with
  the /mcp hint) — there is nothing it can deliver without the application.

IF ANYTHING ELSE IS UNCLEAR: the skill searches the learning file and previous answers first, then
asks with the gap, the affected TCs, the evidence, a recommended answer and its reason, the
alternatives and what stays pending — and never acts on an unanswered recommendation. Your
confirmed answers (never credentials) are saved under "Validation Model (skill 3b)".

============================================================
OUTPUT — WHAT YOU GET (same folder, patched in place)
============================================================
  Testing/Manual_Test/TestCases/[SPEC-{spec-name}/]US-{id}-{name}/
    TEST-CASES-{feature}.md   <- per TC: Validation state (validated / enhanced / inferred /
                                 discrepancy / not-implemented / draft) + an evidence stamp
                                 (date, environment, build, scope, content + requirement hashes);
                                 corrected labels and inserted reveal / wait / trigger steps
                                 (reference tokens [E1] / [A1] / [D2] kept — never a literal);
                                 a TC with a "[HUMAN]" step is walked up to it and ends "draft —
                                 not app-validated (human step pending)", listed under "Needs a
                                 human run"; header: Implementation status, MCP validation (+ "by
                                 3b on {date}, env, scope"), App validation progress;
                                 ## Enhancement Log appended; ## Potential Bugs (PB-n: title,
                                 TC, steps to reproduce, expected, actual); ## Open Questions;
                                 findings buckets. Design fields, TC IDs, coverage score,
                                 traceability and manual-only tables: UNCHANGED.
    TEST-DATA-{feature}.md    <- item statuses from one read-only look each (READY / MISSING /
                                 UNKNOWN), exact values and states seen, extra accounts,
                                 creation ways confirmed available, problems closed or added,
                                 "Environment: {env} checked {date}"
    TC-REVIEW-{feature}.html  <- re-rendered by scripts/render-tc-review.mjs (never hand-edited),
                                 in English unless you pass --lang ar; Arabic pages reuse
                                 TC-REVIEW-STRINGS-{feature}.ar.json — only changed strings need
                                 a new translation; an incomplete translation is delivered as a
                                 clearly marked PREVIEW
    TC-GENERATION-SUMMARY.md  <- status / findings columns patched (multi-story only)
  Testing/project-learning.md <- base URL per environment (no credentials), common flows walked,
                                 labels, locale facts, READY test data, tricks, confirmed Q&A

  APPROVED document: validated READ-ONLY by default (report only, nothing written, approval and
  ADO-MAP intact). With your authorization it is patched; Status becomes PENDING HUMAN REVIEW only
  when something actually changed, and you are told to re-run skill 4 with --republish only when
  an ADO-MAP.md exists for it.

YOUR NEXT STEP: open the page; review "inferred" and "discrepancy" cards with extra care and the
Potential Bugs; answer the open questions; then approve the markdown (or, if it was approved and
changed, re-review and re-approve). Skills 4 and 5 run on the approved document as before.

COMMENTS: type in any comment box on the page, click "Save comments" (save
REVIEW-COMMENTS-{feature}.md beside the page) or "Copy for chat", then say "read my comments".
The next 3b run reads the open comments as hints for the walk and marks each one answered /
declined with a one-line response. A change to a test case's design goes to skill 3 --revision.

WHEN TO RUN: after skill 3, whenever the application is reachable — before approval, after
approval, or again after a new build. Never required.
